# Обнаружение финансового мошенничества в P2P-переводах

## Архитектура сбора и подготовки данных (ETL)
Исходный массив исторических транзакций клиентов (`trans_log`) содержит более **17 миллионов записей**. Прямая обработка и расчет признаков «в лоб» в оперативной памяти Python приводили к избыточному потреблению ресурсов и падению скриптов с ошибкой переполнения памяти (`ArrayMemoryError`). 

Для оптимизации процесса была спроектирована и внедрена эффективная ETL-архитектура:

1. **Хранилище данных (PostgreSQL):** Сырые логи P2P-переводов и общих транзакций были импортированы в локальную СУБД PostgreSQL. Для ускорения последующих операций объединения таблиц (`JOIN`) настроены B-tree индексы по ключевому полю `userid`.
2. **СУБД-агрегация (Сжатие данных):** Генерация признаков (Feature Engineering) профиля клиентов полностью перенесена на сторону СУБД. Расчет исторических агрегированных метрик (`COUNT`, `SUM`, `AVG`, `MAX`, `MIN`, `STDDEV`) выполняется внутри оптимизированного SQL-запроса с группировкой по `userid`. В результате **17 млн сырых транзакций были успешно агрегированы движком базы данных в 3.4 млн уникальных профилей пользователей**, что кратно сократило объем передаваемых в Python данных и полностью решило проблему дефицита RAM.
3. **Оптимизация памяти (Memory Management) в Python:**
   * Чтение данных из БД в Pandas реализовано конвейерным методом — порциями по 100 000 строк через параметр `chunksize`.
   * Применены экономичные типы данных (`float32` для денежных сумм, `int8` для временных меток и флагов), что снизило потребление оперативной памяти на 85%.
   * Тяжеловесное кодирование `pd.get_dummies` заменено на легковесную факторизацию категориальных признаков через `pd.factorize`.
4. **Конвейер выгрузки:** Итоговый собранный датасет объемом **3 452 496** строк автоматически разделяется на обучающую (80%) и тестовую (20%) выборки. Для сохранения экстремального дисбаланса целевого класса (0.08% фрода) строго в обеих частях применена **стратификация** (`stratify=y`). Результат перезаписывается в БД (`train_dataset`, `test_dataset`) и дублируется на диск в локальные `.csv`-файлы в директорию `data/processed/`.

## Первичный анализ данных (EDA) и предобработка
Финальная выборка, полученная в результате работы ETL-пайплайна, содержит **3 452 496** строк. Доля целевого класса `isfraud` составляет всего **0.08%** (`2 818` транзакций), что классифицирует задачу как задачу с экстремальным дисбалансом классов. 

В ходе разведочного анализа данных (EDA) в Jupyter-ноутбуке были выполнены следующие шаги по аналитической очистке датасета:

### Очистка от мультиколлинеарности и неинформативных фичей
* **Устранение мультиколлинеарности:** Из датасета были удалены сгенерированные на этапе ETL признаки `trans_mean`, `trans_max` и `trans_std`. Анализ матрицы корреляций выявил их экстремально высокую линейную зависимость (коэффициент корреляции Пирсона $\ge 0.98$) с базовым признаком совокупных трат `trans_sum`. Исключение этих дублирующих фичей необходимо для предотвращения дестабилизации весов и переобучения линейных моделей.
* **Удаление констант:** Исключен признак `currency`, так как после проверки распределения он принял значение `0` (одна валюта) для всей выборки, следовательно, не несет никакой предсказательной силы для алгоритмов машинного обучения.

### Выявленные временные закономерности
* **Паттерны суток** (`hour`): Абсолютный пик мошенничества зафиксирован в 18:00 (конец рабочего дня, снижение бдительности жертв). Также выделяются ночные пики в 01:00 и 03:00 (расчет на то, что жертва спит и не успеет оперативно заблокировать карту). Провал в 02:00 связан с периодом проведения технических работ на банковских шлюзах.
* **Паттерны недели** (`day_of_week`): Пятница (4) — наиболее опасный день с максимальной долей фрода в общем объеме трафика. Суббота (5) — самый безопасный день, что объясняется переходом пользователей на офлайн-покупки через торговые терминалы.
