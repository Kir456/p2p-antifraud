# Анализ данных  и предобработка

**Задача:** Подготовка данных для построения модели обнаружения мошеннических P2P-переводов (`isfraud`).
**Исходный объем данных:** 3 452 496 строк.
**Итоговый объем после очистки:** 3 443 864 строки (сохранено 99.75% данных).

---

## 1. Очистка данных и борьба с аномалиями

### Мультиколлинеарность
При анализе матрицы корреляций выявлена жесткая линейная зависимость ($r \ge 0.98$) между историческими агрегатами трат пользователя: `trans_sum`, `trans_mean`, `trans_max` и `trans_std`. 
* **Решение:** Чтобы избежать дестабилизации весов моделей (особенно линейных), признаки `trans_mean`, `trans_max` и `trans_std` были удалены. Оставлен один базовый агрегат — `trans_sum`.
* **Дополнительно:** Столбец `currency` содержал константное значение `0` для всех строк и был удален как неинформативный.

### Обработка экстремальных выбросов (`amount`)
В распределении сумм текущих P2P-переводов (`amount`) обнаружен тяжелый хвост с аномалиями до 220 000 000. Проверка топ-70 крупнейших транзакций показала, что все они являются легитимными (`isfraud == 0`), то есть представляют собой нецелевой шум (транзакции крупных клиентов или юрлиц).
* **Решение:** Проведена фильтрация по квантилю **99.75%**. Порог отсечения составил **678 330.24**. 
* **Результат:** Удалено всего 8 632 строки шума. Потеря целевого класса минимальна — удалено 6 примеров фрода из 2 818 (0.21% от общего объема мошенничества), что абсолютно безопасно для обучения.

## 2. Ключевые инсайды временных признаков

### Паттерны по часам суток (`hour`)
* **Пик в 18:00:** Самое большое абсолютное количество фрода. Совпадает с концом рабочего дня, когда люди массово совершают P2P-переводы и невнимательны.
* **Ночные всплески (01:00 и 03:00):** Мошенники активизируются ночью, рассчитывая на то, что жертва спит и не сможет быстро заблокировать карту.
* **Провал в 02:00:** Технический артефакт (вероятное время клиринга или банковских обновлений, когда падает общий поток транзакций).

### Паттерны по дням недели (`day_of_week`)
* **Пятница (4):** Самый высокий риск фрода. Максимальная доля мошеннических операций от общего объема.
* **Суббота (5):** Самый безопасный день. Мошенническая активность резко снижается, так как пользователи переходят на офлайн-траты.

## 3. Техническое задание для этапа моделирования (Советы команде)

Передаю вам очищенный файл `data/cleaned_dataset.csv`. При написании кода для обучения модели соблюдайте следующие требования:

1. **Экстремальный дисбаланс классов:**
   Доля фрода в датасете составляет всего **0.08%** (2812 строк против 3.4 млн). 
   * **Обязательно** при разбиении выборки (`train_test_split`) используйте параметр `stratify=y`.
   * **Запрещено** использовать метрику `Accuracy`. Качество оценивать строго по `ROC-AUC` и `Average Precision` (PR-AUC).
   * В моделях обязательно включайте балансировку классов (например, `class_weight='balanced'` для LogisticRegression / RandomForest или `scale_pos_weight` для XGBoost).

2. **Масштабирование признаков:**
   Исторические колонки `trans_sum` и `trans_min` сохранили свои длинные хвосты (до 300 млн для общей суммы трат). 
   * Для линейных моделей и нейросетей перед обучением **необходимо** использовать `RobustScaler` вместо `StandardScaler`, либо предварительно логарифмировать эти признаки через `np.log1p()`.
   * Для моделей на основе деревьев решений (`LightGBM`, `XGBoost`, `CatBoost`, `RandomForest`) масштаб не важен, можно подавать данные без изменений.

3. **Кодирование времени:**
   Признаки `hour` и `day_of_week` оставлены в исходном числовом виде для сохранения гибкости. 
   * Если будете обучать **логистическую регрессию**, обязательно переведите их в циклические фичи через синус и косинус:
     $$\text{hour\_sin} = \sin\left(\frac{2\pi \cdot \text{hour}}{24}\right), \quad \text{hour\_cos} = \cos\left(\frac{2\pi \cdot \text{hour}}{24}\right)$$
   * Если будете использовать **бустинги**, оставьте их как есть или переведите в тип `category`.

4. **Генерация новых признаков:**
   Признак `amount_to_mean_ratio` - отношение текущего перевода к среднему чеку
   Признак `is_weekend` - бинарный признак, где 1 - выходной, 0 - будни
